GETTING STARTED

Understand your evidence

DataVouch helps you decide whether a data workload change meets your checks. Start with a business question, compare original and changed executions, then inspect the evidence.

Choosing a cloud project

When your administrator enables Google Cloud discovery, New experiment lists projects visible to the backend cloud identity and approved for your access. Select a project and Load locations before filling out the experiment. Refresh cloud metadata updates the list. Locations come from visible datasets and recent jobs; an empty list may mean missing permissions or no visible metadata. Ask your administrator to configure an explicit connection if needed.

What is a workload?

A workload is a named piece of data processing with a stable purpose, such as daily revenue, an inventory refresh or a customer aggregate. Keep the same workload name when testing different changes to that work. A workload is not a cloud project, connection or single job.

For example, Daily revenue could have experiments for a SQL rewrite and a partitioning change. Each experiment compares a baseline with one candidate.

The Workloads page shows imported catalog reports and workloads registered through saved runs. Catalog entries are read-only examples or imported evidence. Saved runs are collected by this deployment. DataVouch does not discover or schedule all jobs in your cloud account.

Different workload examples

  • Revenue or financial aggregates: independently compare totals, refunds and currencies.
  • ETL and ELT transformations: check business rules, schema and output checksums.
  • Incremental refreshes: check freshness, duplicates and missing records against a known input snapshot.
  • Query and resource optimizations: compare runtime, slot consumption or bytes while proving the business result is preserved.

These are use cases, not separate product modes. Live collection currently supports BigQuery job metadata. Other platforms need an adapter. Pipeline-wide checks require suitable evidence; DataVouch does not orchestrate the pipeline.

Daily summary in the bundled catalog contains synthetic reports. Order revenue, when the local demo is loaded, contains measured SQLite examples. Neither is your production data.

Why do reports look different?

Comparison reports evaluate one performance or resource metric; correctness remains UNKNOWN. Verification reports combine configured performance, correctness, execution-window and reliability checks. Financial reports evaluate supplied pricing, spending and attribution evidence. These are report types, not different workload providers.

What is a new experiment?

An experiment describes one proposed change and how to judge it. The baseline is the original version; the candidate is the changed version. Both need comparable inputs and execution conditions.

  1. Select an administrator-approved project and location.
  2. Name the workload and experiment, and describe the change.
  3. Supply the completed baseline and candidate job IDs and their UTC windows. End times are exclusive.
  4. Choose a metric, regression limit, minimum sample count and reliability policy.
  5. Supply independently checked correctness evidence. Missing evidence must remain missing.
  6. Validate the plan, then explicitly run collection if enabled.

Validate plan checks the inputs; it does not query the cloud or produce a verification PASS. Run experiment collects metadata for existing jobs. It does not execute your workload SQL or correctness assertions. Collection can incur query charges.

What are runs?

A DataVouch run is a saved execution of an experiment plan: its inputs, collection state, measurements and report. It can include many baseline and candidate cloud jobs. A cloud job is one source execution; a DataVouch run is the evaluation of the selected groups.

RUNNING means collection is in progress. COMPLETED means a report was produced, even if its conclusion is FAIL or UNKNOWN. ERROR means collection or processing failed and needs investigation.

The same plan submitted again in the same execution context reuses its saved result. Use a new experiment identity for a distinct evaluation. Administrators can delete individual, selected or all permitted history after confirmation. Deletion removes local plans and reports, not cloud jobs, imported catalogs, backups or audit events.

How to read a result

  • PASS: the configured checks passed with sufficient supplied evidence.
  • FAIL: a required check failed. A faster query can still be wrong.
  • UNKNOWN: evidence is missing, insufficient or unsuitable. It is not approval.

A required failure takes precedence over missing evidence. Inspect each check and its explanation. PASS does not establish whole-system correctness, causation or future reliability. Matching row counts alone do not prove correctness.

In the measured revenue demo, the correct total is 882,150 cents. A rewrite that ignores quantities returns 441,075 cents. It can run faster and complete successfully, but the business check must fail.

Financial assessments are separate: reduced runtime or bytes do not prove a lower bill. Estimates use declared pricing; spending and attribution require matching supplied financial evidence.

Access and deployment

Viewers inspect permitted results. Operators also plan, collect and assess financial evidence. Administrators also delete history and export scoped audit events. Shared deployments use the client's existing identity gateway; credentials stay on the backend.

This release supports one active experiment and up to 50 saved runs per deployment. Use the repository's client-validation and independent-review guides before shared production use.
