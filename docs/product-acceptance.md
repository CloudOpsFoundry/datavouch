# Product acceptance

DataVouch verifies whether a declared data workload change meets configured correctness, performance and reliability policies, then evaluates financial evidence when supplied. Its initial provider is BigQuery; the shared contracts support additional adapters. The UI, CLI and workflow gates use the same engines.

## Delivery coverage

| Product requirement | Delivered path | Validation |
| --- | --- | --- |
| Register a workload | UI workload identity, saved workload catalog | Planner and history tests |
| Capture historical baseline | Selected completed jobs and UTC windows | BigQuery fixture and bounded sandbox collection |
| Declare candidate/change | Guided plan, change time and reference | Plan validation and window tests |
| Ensure comparability | Snapshot, environment and attested comparison contract | Engine and adapter contract tests |
| Compare performance | Runtime, slot consumption, processed/billed bytes | Metric and threshold tests |
| Check correctness | Guided assertion plus advanced schema/hash/freshness/row-count evidence | Correctness tests; browser PASS/FAIL/UNKNOWN journeys |
| Measure reliability | Complete execution cohorts and failure thresholds | Failed-job fixtures and sandbox failed-job evidence |
| Handle missing evidence | Explicit UNKNOWN with reasons | Unit, integration and workflow gates |
| Evaluate cost | Bound pricing estimates and supplied billing evidence | Exact arithmetic and UI/core parity |
| Prevent unsupported savings | Reviewed attribution, claim overlap checks and matching verification | Financial contracts and failure cases |
| Reproduce a result | Saved input, deterministic reports and CLI replay | Byte-level UI/CLI parity and package regression |
| Inspect results | History, measurements, reasons and downloads | Authenticated route and UI checks |
| Integrate CI | Gate policy with explicit UNKNOWN behavior | Self-hosted workflow checks |
| Extend providers | Versioned adapter registry and fixture adapter | Independent package contract tests |
| Deploy locally | Python 3.15 monorepo and application container | Installed-package and container smoke checks |
| Authorize teams | Existing OIDC gateway, roles, connection scopes | Header forgery, scope, role and revocation tests |
| Govern retained evidence | Private run store, audit events and admin deletion | Persistence, recovery and deletion tests |
| Prepare public release | License, contribution/security guides and release checks | Local automated checks; independent gates below |

The initial product uses explicit workload registration; it does not automatically discover every workload. Financial evidence is supplied, not collected from billing APIs. Correctness is evaluated from supplied evidence, not generated by executing customer assertions. These boundaries prevent unsupported claims and uncontrolled customer queries.

## Final acceptance before publication

1. Complete [the sandbox UI walkthrough](sandbox-acceptance.md), recording actual expected and observed outcomes.
2. Validate the client's real OIDC gateway, identity provider, TLS and private-network boundary using [gateway acceptance](gateway-access.md#operations-and-acceptance).
3. Have an independent user follow installation and replay the examples. Resolve material usability findings.
4. Complete independent security and license review, including source/history secret review and dependency findings.
5. Approve the public CI trust model before changing repository visibility. Never run untrusted public contribution code on a privileged persistent self-hosted runner.
6. Review the exact PR revision and its checks, then explicitly authorize publication and release artifacts.

A passing test suite is engineering evidence; it does not complete these independent acceptance steps. The repository stays private and the version stays experimental until the release gates are satisfied.
